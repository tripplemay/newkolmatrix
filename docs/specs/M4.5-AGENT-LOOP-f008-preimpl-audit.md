## 1. 实物证据（读的是本仓 node_modules，不是网络资料）

版本实物：`ai@7.0.31`、`@ai-sdk/react@4.0.34`、`@ai-sdk/openai@4.0.16`（provider spec `v4`）。

| # | 事实 | 证据位置 |
|---|---|---|
| E1 | **工具入参可增量流**：UI 层有一等状态 `state:'input-streaming'`，携带 `input?: DeepPartial<TOOL['input']>` | `ai/dist/index.d.ts` `UIToolInvocation` |
| E2 | wire 层有对应片：`tool-input-start` / `tool-input-delta` / `tool-input-end` | `@ai-sdk/provider` `LanguageModelV4StreamPart` |
| E3 | **工具产物也可流**：`ToolExecuteFunction` 返回类型是 `AsyncIterable<OUTPUT> \| PromiseLike<OUTPUT> \| OUTPUT` —— execute 可写成 async generator 逐段 yield | `@ai-sdk/provider-utils/dist/index.d.ts` |
| E4 | 无 `tool-output-delta` / `output-streaming` 这类命名 —— 产物流是靠 E3 的 AsyncIterable，不是独立协议片 | 全文 grep 无命中 |
| E5 | 现状：`CopilotPanel.MessageParts` 只在 `state === 'output-available'` 渲染画布，其余状态一律显示「调用工具 X…」一行字 | `src/components/copilot/CopilotPanel.tsx` |

**结论：SDK 侧两条路都真实存在，不需要降级为「假装渐进」。**

## 2. 但 acceptance 点名的工具落在哪条路上？—— 决定性事实

acceptance 写的是「draft 类工具输出（`draft_email` / `draft_report`）在画布卡渐进出现」。核实物：

- `draft_email` / `refine_email`（`tools/email-drafting.ts`）与 `draft_report`（`tools/draft-report.ts`）的**入参只有 id 与选项**（`projectId` / `period` / `kolId` 等）；
- **草稿正文是 execute 内部再调网关生成的产物**，属于工具 **output**。

于是：
- **E1/E2（入参流）对这三个工具完全无效** —— 模型没在写正文，它只写了一个 `projectId`。入参流能渐进渲染的是「模型自己逐 token 写出来的字段」，本批里符合这个形态的是 `propose_plan`（模型逐条写计划 items）。
- 要让 draft 正文渐进出现，只能走 **E3（execute 返回 async generator）**，且需要起草服务改成流式网关调用。

## 3. 三个方案

| 方案 | 做什么 | 真渐进？ | 代价 / 风险 |
|---|---|---|---|
| **A · 工具产物流式** | 起草服务改流式网关调用；`toAiSdkTools` 的 execute 改 async generator 逐段 yield | ✅ 是（正文边生成边出现） | **撬动柱一契约**：`executeTool` 现在返回 `ToolResult`（一次性），要引入流语义；闸门 / zod 校验 / outbound pending 信封都在这条路径上。F008 是 low 优先级 feature，为它改唯一执行入口的返回契约，风险与收益不匹配 |
| **B · 结果分段渲染（P8 预设的降级）** | 产物到齐后前端按段落分批显示（打字机式） | ❌ 否 | 零后端改动。但**数据其实已经全到了，只是延迟显示**——这是在演一个「正在生成」的假象。与本项目「不假造进行中状态」的诚实口径直接冲突 |
| **C · 入参流式渲染（改覆盖面）** | 用 E1 的 `input-streaming` + partial input 渐进渲染**模型自己在写**的工具卡（本批 = `propose_plan` 计划卡：标题→逐条步骤边写边出） | ✅ 是 | 零后端改动、零契约撬动。但覆盖面不是 acceptance 点名的 draft 类工具 |

## 4. Generator 的建议（不作数，供裁决参考）

建议 **C**，并把 A 登记进 backlog：

1. B 是唯一「按 acceptance 字面交付」的选项，但它交付的是假象。宁可少做一个特性，不做一个演出来的特性。
2. C 是本批唯一「真渐进 + 零契约风险」的组合，且计划卡（F004）恰好是本批新增、最长、最值得边写边看的产物。
3. A 值得做，但它本质是「柱一执行入口支持流式产物」的架构升级，应该独立立项，而不是挂在一个 low 优先级的渲染 feature 下顺手改。
