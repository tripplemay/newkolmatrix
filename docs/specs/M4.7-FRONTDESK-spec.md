# M4.7-FRONTDESK 批次规格（单一前台：专家降为内部能力）

> 状态：**待用户裁决**。裁决点 D-1..D-7 逐条确认后才写 features.json 开工。
> 触发源：2026-07-26 生产手测。用户在项目环节页问「帮我看看这个项目该推进什么，然后分析下 ROI」，匹配 Agent 拒答并口头让用户「去找洞察 Agent / 编排 Agent」。

---

## 1. 根因与方向

**根因不在跳数或预算，在于「页面路由决定谁来回答」。**

`defaultAgentForRoute(route)` / `STAGE_AGENT[stage]` 把用户落在哪个页面，映射成「哪个专家有发言权」。于是内部的人格分区变成了用户要面对的墙：跨专家的问题必然撞墙——要么被拒（今天的行为），要么身份来回横跳（曾提的方案 A）。两者都是让用户替我们的组织架构买单。

**已否决的方案 A（给环节人格发 `handoff_to`）**：2026-07-26 用户复议后撤销。理由是只改跳数/预算属治标，且做完即被本方案取代，还要多维护一套负向断言。

**方向：单一前台 + 专家降为内部能力。** 这不是新发明——`docs/dev/architecture.md:1086`「协同交接两种实现形态」表的第二列**子 Agent 调用（演进）**：「某工具 `execute` 内部再起一次 generateText（子专家 prompt + 子工具集）」，状态一直是**未实装**。本批把它实装。

| | 现在 | 目标态 |
|---|---|---|
| 用户面对 | 页面对应的那个专家 | **始终同一个助手（前台）** |
| 页面上下文 | 决定谁有发言权 | 降级为**线索**（当前项目/环节 = 关注点，不是权限） |
| 跨专家问题 | 撞墙 → 拒答 / 身份横跳 | 前台内部咨询专家，**用一个声音**答完 |
| 专家在界面上 | 顶部身份卡换人 | 一行可展开的痕迹（「咨询了匹配专家 · 读了 3 组组合」） |

---

## 2. 红线不变（本批不碰，且必须有负向断言证明没碰）

1. **outbound 两步票据闸门**：子 loop 里调 outbound 工具，同样停在 pending，必须人确认后 confirm + execute 才发生副作用。`executeTool` 仍是唯一入口，`ctx.confirmationToken` 仍只由 gate 签发。
2. **时刻隔离（P1 / DP-3）**：子 loop 的可见工具 = 目标人格子集，且执行侧同样按目标人格拦（不能只靠 `activeTools` 收窄视野——`to-ai-sdk-tools.ts` 的 `isToolActive` 双保险照旧）。
3. **行动承诺诚实**：前台综合专家结果时不得把「证据不足」圆成结论、不得宣称未发生的动作已完成。
4. **例程零直通**：本批不动例程。

---

## 3. 待裁决点

### D-1 · 子 loop 里备好的 pending 记在谁名下

**现状（实物）**：`gate.ts:128` 用 `ctx.agentId` 写 `PendingAction.agentId`，而 `ctx.agentId` 在 M4.5 的接力里**不更新**（soft-watch O-G2-1 已记）。单一前台之后，所有 pending 都会记成「前台」，专家干的活全挂前台名下；今天页雷达深链的 `agentId → STAGE_AGENT` 反查会全线落回退分支（`orchestrator` 不在 `STAGE_AGENT` 值域）。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 子 loop 内 `ctx.agentId` 派生为目标人格；`PendingAction.agentId` / `OperationLog.actor` 记**实际干活的专家** | 要改 ctx 派生链；顺带闭环 O-G2-1 |
| B | 保持记前台，另加 `PendingAction.viaAgentId` 字段记专家 | 加字段 = 迁移；雷达反查仍要改 |
| C | 不动，接受错标 | 雷达深链持续落回退分支，留痕失真 |

**推荐 A。** 理由：留痕的意义是「谁做的」，记成前台等于把审计信息抹平；且 O-G2-1 已经欠着，本批不还只会更贵。

---

### D-2 · 前台与专家结论冲突时以谁为准

**风险具体化**：洞察专家返回「ROI 证据不足，分子缺失」，前台在综合时可能圆成「ROI 大约 1.8x」。这是诚实条款的新战场——M4-INSIGHT 好不容易钉住的「分子缺显证据不足绝不填 0」，可能在前台这一层被重新抹平。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 专家结果**原样透传**：前台可以组织语言，但不得改写专家给出的结论性字段（数值 / 证据充分性 / 状态）。前台 system 加硬条款 + 单测钉文案锚点 + 变异测试 | 前台叙述自由度受限 |
| B | 前台可覆盖，但必须标注「前台判断」 | 用户要分辨两层可信度，认知负担转嫁 |
| C | 专家结果直接呈现，前台只做串场 | 回到「多个声音」，违背本批目的 |

**推荐 A。** 并且建议：专家返回的结构化结果里，**证据不足类字段单独成型**（如 `insufficientEvidence: true` + `reason`），前台 prompt 明写「该字段为真时不得给出数值结论」，这样可以机械断言而非靠文案自觉。

---

### D-3 · 成本硬上限

嵌套 loop 让 token 与延迟成倍。现状：常规人格 5 步、深链 10 步、`maxDuration=120s`。真实延迟属 L2，**至今无实测数据**（全批验收皆 mock）。

| 参数 | 推荐值 | 说明 |
|---|---|---|
| 每轮最多咨询专家数 | **2** | 覆盖「推进什么 + ROI」这类双专家问题 |
| 单个子 loop 步数 | **≤3** | 专家只做一件事：读数据 + 给结论 |
| 前台自身步数 | **5**（不变） | 前台不干活，只分派与综合 |
| 总步数硬顶 | **前台 5 + 子 loop 2×3 = 11** | 与现有深链 10 同量级 |
| 撞顶行为 | **必须诚实告知**「未答完 + 还差什么」 | 变异测试钉死，不许假装答完 |

**这几个数字是猜的，我如实说明。** 建议做成**配置常量**（registry 单一真相源），上线后拿到真实延迟再调，而不是写死在代码各处。

### D-4 · 咨询失败/超时怎么办

| 方案 | 做法 |
|---|---|
| **A（推荐）** | 前台如实说「我问了洞察专家但没拿到结果（原因）」，并给出它自己能给的部分。**绝不假装咨询过**，也绝不用自己的猜测填补 |
| B | 静默降级为前台自答 | 违背诚实条款，否决 |

**推荐 A**，且咨询失败必须留痕（`OperationLog`），否则线上无法归因。

---

### D-5 · `Handoff` 表与协同交接可视化的去留

**取证**：`Handoff` 表目前只有一个真实读消费者（`src/app/api/handoffs/route.ts`），前端四个组件消费（`HandoffCollab` / `HandoffCard` / `HandoffPanel` / `PersonaSwitchNote`）。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 表与可视化**保留**；子 Agent 咨询**也落 Handoff 行**（fromAgent=前台, toAgent=专家），成为「协作痕迹」的统一数据源 | 语义从「交接」扩为「协作」，需改注释与文档 |
| B | 保留表但咨询不落行，Handoff 仅留给跨会话人工交接 | 界面上的协作痕迹要另起数据源 = 重复建设 |
| C | 废弃表与四个组件 | 丢掉已建成的可视化，且跨会话交接场景没了载体 |

**推荐 A。** 需要你判断的产品问题：**单一前台之后，用户还需要看到「谁交接给了谁」吗**，还是只关心「结果怎么来的」？我倾向前者仍有价值（可解释性 + 审计），但如果你认为用户不关心，B 更省。

---

### D-6 · 子 loop 的模型从哪来（注入缝纪律）

**问题**：`ToolContext` 里没有 model。`consult_specialist` 的 `execute` 要起子 loop，就得拿到一个 `LanguageModel`。

M4 的教训写在 `agent-architecture.md`：**注入缝传入即无条件使用**，不得因凭据缺失把注入的 model 改道回默认 caller，否则 CI（无凭据）下 mock 测试静默走降级分支，测的不是被测对象。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | `ToolContext` 增可选 `model?: LanguageModel`，由 `runAgentLoop` 把自己的 model 传下去；子 loop 用 `ctx.model ?? chatModel()` | ToolContext 多一个字段，所有构造点要过一遍 |
| B | `consult_specialist` 直接 `chatModel()` | 测试无法注入 mock → 子 loop 只能真外呼才测得到，等于放弃 L1 覆盖。**否决** |

**推荐 A**，且必须有一条测试钉死：注入了 model 就绝不回落默认 caller。

### D-7 · 前台是谁

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 复用现有 `orchestrator` 人格作为前台，扩其职责与工具（+`consult_specialist`） | 改动最小；但 orchestrator 的 duty 文案要改（不再是「环节调度」，而是「受理与综合」） |
| B | 新建一个 `frontdesk` 人格 | 名册多一个成员，registry / 文档 / 名册段全要动；旧 orchestrator 何去何从需另裁 |

**推荐 A。**

## 6. 测试策略（吸取本日教训，写进 acceptance 而非靠自觉）

1. **凡「不得编造 / 不得出现」类断言，一律写成正向精确匹配**（M4.6 复验实证：黑名单不可穷尽，两种编造形态绕过）
2. **每条新断言必须附带「什么改动会让它红」的变异记录**，且变异要包含**作者没想到的绕过路径**（本会话内「取证器看不见目标」撞了三次）
3. **机械钉的覆盖面必须与它守护的那句话逐项对齐**（N-1 段 = 静默门）
4. **mock 测试床把入参写死会掩盖「模型能否自己发现入参」类缺陷**（M4.6 缺陷正身）——凡模型需自填的入参，acceptance 单列装配层断言
5. **清理段：软引用表（`OperationLog` / `Handoff`）不级联，必须逐表清 + 逐表断言残留**

## 7. 风险与代价（如实登记）

- **成本成倍**：一个问题可能烧掉十几次模型调用。D-3 的数字是猜的，无真实延迟数据支撑。
- **延迟**：交接条款要求专家「重读真实数据」，每个专家都要打库，串行叠加。`maxDuration=120s` 有撞墙风险。
- **前台成为新的单点**：前台 prompt 的质量直接决定整体体验；它一旦分派错专家，用户看不见内部结构、更难自救。
- **可解释性下降**：专家隐入内部，用户不再看到「谁在说话」，出问题时归因更难——D-5 的协作痕迹是对冲手段。
- **本批不解决的**：真实模型质量（属 L2）、跨轮记忆、并行咨询的结果合并冲突。

## 8. 不做什么（范围边界）

- 不动闸门、不动例程、不动画布渲染既有分支
- 不引入新的人格成员（D-7 取 A 时）
- 不做跨轮对话记忆（前台常驻 ≠ 记住上一轮的专家结论）
- 不做并行咨询的智能合并（两个专家结果由前台顺序综合，不做冲突消解算法）
