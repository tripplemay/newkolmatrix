## 1. 背景与目标

### 1.1 现状（实测，2026-08-06）

M5-AUTH-RLS 已把 RLS **地基**做完并部署到生产：24 张表 default-deny policy、`kol_app`
非特权角色已建、BYPASSRLS 启动哨兵已装、`DB_APP_ROLE_RUNTIME` 开关已留。生产实证
「kol_app 未设变量 Project=0 行 vs 特权 6 行」。

但**运行时仍走特权连接**（`DB_APP_ROLE_RUNTIME` 未设），因此：

- 对产品实际跑的那条连接而言，RLS 是**惰性的**——租户隔离仍然只由应用层 `where` 一道保证；
- 启动哨兵持续打印「RLS 不生效」告警（刻意可见态，不是噪声）；
- `tests/unit/project-scope-census.test.ts` 的三口径普查钉仍是**主力防线**而非二线。

### 1.2 为什么不能直接把开关打开

F009 开工前审计用真库 + 真 RLS + 真 kol_app 连接实测，证伪了 spec D-7 字面机制的两个前提
（证据原样见审计 §1，探针 `scripts/test/f009-injection-probe.ts` 仍在仓内可复现）：

| 编号 | 实测事实 | 后果 |
|---|---|---|
| B1-2 | `$extends` 挂 `$allModels` 时，紧随的 raw 查询得 0 行 | 6 处产品 raw SQL 不在覆盖面内 |
| B1-3 | interactive 事务连接上 `app.tenant_id` 为空，同段代码却查到 3 行 | 查询没在调用方事务里执行 |
| **B1-4** | 调用方事务回滚后，事务内写的那行**仍在** | `$transaction` 原子性被**静默**废掉 |
| **B3** | `set_config(local=false)` 后 12 次并发查询有 1 次看得见数据 | 会话变量粘连接池 = 跨租户泄漏面，比没有 RLS 更坏 |
| B2-1/2/3 | 登录查用户 / 注册建租户 / slug→租户解析在 kol_app 下分别得 null / 被拒 / null | **切过去就没人能登录** |

### 1.3 本批目标（一句话）

**让「机制成立」有定论**：把 `withTenant` + ALS 的注入底座、双 client 引导白名单、以及
防漏的普查钉建起来，并用一条**开关真开着**的最小闭环证明它能跑通；全站入口收口与生产切换留 M5.2。

**本批不做**：`DB_APP_ROLE_RUNTIME` 默认值不变（仍默认关）；不触发部署；不改生产配置。

## 3. 关键设计决策

### D-1 · 注入落点 = ALS 感知代理（用户 2026-08-06 实答）

预裁决 Q2:B+C 定了**机制**（withTenant 保事务内 SET LOCAL 为底座，ALS 只负责租户来源），
但未定**落点形态**。本批裁定用代理，不逐个改写调用点。

**实测底数（`grep` 当场取，非转述）：**

| 面 | 实测值 |
|---|---|
| `src/` 下 import `db/prisma` 的文件 | **73** |
| 模型调用点（`prisma\|db\|tx.<model>.<op>`） | **206**（其中 `tx.` 前缀 34） |
| `$transaction` 调用点 | **15 处 / 10 文件** |
| 产品 raw SQL（不含 `app-role.ts` 自身基建 2 处） | **6 处 / 4 文件** |
| `tests/` 下直接 import 单例的文件 | **85 / 142** |

**理由（可复用）：**

1. 裁决选 Q2-C（ALS）的**原始理由就是「调用点改动小得多」**；逐个改写 206 处等于付了 ALS 的
   复杂度却不收它的收益。
2. M5 已确立的 **D-8「不为 RLS 翻修既有测试」** 是本项目现行原则；改写 85 个测试文件是正面推翻它，
   且会把「机制对不对」与「改写有没有改错」两类失败混进同一轮验收。
3. 裁决对例外的实质要求是「**可数、可钉、可复查**」。代理方案照样满足：引导点显式 `import
   { privilegedDb }`，普查钉照做（判据甚至更简单——白名单 = import 该模块的文件集）。

**代价（如实登记，不美化）：** 「忘了包裹」在源码里**不可见**，只在运行时暴露。这比显式访问器
的编译期可见性弱。对冲手段两条，缺一不可：① 开关开 + 无 ALS 作用域时**抛专用错误**（不是静默零行）；
② 入口面覆盖普查钉（F007 交付清单，M5.2 收口）。

### D-2 · 三层 client 分工

| 名字 | 连接串 | 谁能用 | RLS 对它 |
|---|---|---|---|
| `privilegedDb` | 恒 `DATABASE_URL`（dev=kol / prod=kol / CI=postgres） | **仅引导白名单**（F003 普查产出） | 绕过（owner / BYPASSRLS） |
| 运行时 client | `DB_APP_ROLE_RUNTIME=1` → `DATABASE_URL_APP`；否则 `DATABASE_URL` | 仅 `withTenant` 内部开事务用 | 开关开时**真实生效** |
| `prisma`（导出名不变） | —— | 全部既有调用点 | 见 D-4 |

`resolveRuntimeDatabaseUrl` / `resolveAppDatabaseUrl` / `isAppRoleRuntimeEnabled` 已存在于
`src/lib/db/app-role.ts:91-117`，**复用，不重写**。

> **刻意不动 `schema.prisma` 的 datasource**——那会把 `prisma migrate` 的连接一起改掉，
> 而迁移必须保持特权（M5 D-5 已定，`src/lib/db/prisma.ts:14-19` 有原文）。

### D-3 · `withTenant` 语义（三条硬语义，逐条可测）

```ts
withTenant<T>(tenantId: string, fn: (tx: TenantTx) => Promise<T>): Promise<T>
```

1. **事务内 SET LOCAL**：内部开 interactive `$transaction`，第一条语句
   `set_config('app.tenant_id', $1, true)`（第三参 `true` = `is_local`，事务结束即失效）。
   policy 实物形状见 `prisma/migrations/20260804180000_m5_rls_tenant_isolation/migration.sql:32-36`：
   `USING ("tenantId" = current_setting('app.tenant_id', true))`，双侧同式。
2. **嵌套复用，不开第二事务**：`withTenant` 内再调 `withTenant`（同租户）必须复用既有 tx，
   不得开新事务、不得重设变量。这是 B1-4 的根治点——原子性归调用方所有。
3. **不同租户嵌套 = 抛**：`withTenant(A)` 内调 `withTenant(B)` 必须抛错，不得静默切换或静默沿用 A。

### D-4 · 双态语义：开关关 = 逐位不变；开关开 + 无作用域 = 抛

| 状态 | `prisma` 代理解析为 | 理由 |
|---|---|---|
| ALS 有租户事务 | 该事务的 tx client | 正常路径 |
| 无 ALS + 开关**关** | 运行时 client（= 特权，行为与今日一致） | **D-8 继承**：既有 142 个测试文件、dev server、scripts 零改动零影响 |
| 无 ALS + 开关**开** | **抛 `MissingTenantScopeError`** | fail-closed。回落到「无变量的 kol_app 查询」= 静默零行，是 M5 F007 注释 `app-role.ts:98-107` 点名要避免的失败模式 |

`$transaction` 在代理上的行为：ALS 有事务时 `TransactionClient` **没有** `$transaction` 方法 →
15 处调用点必须迁移到 `withTenant`（F004）。这是本批唯一必须改写的调用点类别。

### D-5 · 引导白名单由**普查产出**，不照抄审计

审计（2026-08-04）写「引导查询点当前 = 3 个」。**该数字已过期**——M5 F006 的登录留痕在同批落地后
新增了引导写路径。本批实测（2026-08-06，`grep` 取）：

| # | 位置 | 动作 | 为什么必须特权 |
|---|---|---|---|
| 1 | `src/lib/auth/index.ts:25` | `prisma.user.findUnique({email})` | 登录：租户是这次查询的**产物**（B2-1） |
| 2 | `src/lib/auth/index.ts:61` | `prisma.user.findUnique({email})` | 失败登录归因到被撞库的租户，此刻无会话 |
| 3 | `src/lib/auth/index.ts:53,72` → `audit.ts:137` | `tenant.upsert('__auth-audit__')` | 占位租户，写的是**非当前租户**的行，USING+WITH CHECK 双向拒 |
| 4 | `src/lib/auth/index.ts:53,72` → `audit.ts:138` | `operationLog.create` | 同上 |
| 5 | `src/lib/auth/register.ts:107` | `$transaction`→`tenant.create`+`user.create`+`operationLog.create` | 要建的租户此刻还不存在（B2-2） |
| 6 | `src/lib/agent/context.ts:31` | `prisma.tenant.findUnique({slug})` | `systemContext` 第一步，无会话面依赖它（B2-3） |
| 7 | `src/instrumentation.ts:14-18` | `runConnectionRoleSentinel(prisma)` | 启动期哨兵，无租户可言；必须问到**真实运行时连接**是谁 |

**≥7 处 / 4 文件。** Generator 开工时**必须重跑普查**并以实测结果为准——本表是 spec 起草时刻的快照，
不是白名单的真相源。任何增删都要在白名单旁写明理由。

> `src/lib/auth/rate-limit.ts` 与 `dev-seed.ts` 实测**不碰库**（`grep` 零命中），不入白名单。
> `audit.ts` 本身通过 `db: AuthAuditDb` 参数接收 client，注入点在调用方，故白名单登记调用方而非它。

### D-6 · 本批止于「最小闭环」，全站收口留 M5.2（用户 2026-08-06 实答）

**理由：** 审计 Q3 把 F009 移出 M5 的理由正是「全站切非特权连接会让验收面变成整站回归」。
一批做完等于把当初拒绝的东西原样吃回来。拆开后：M5.1 的验收面是**机制**（可用变异证活穷尽），
M5.2 的验收面是**覆盖面**（可用清单差集穷尽）——两类失败不混在同一轮里。

**M5.1 最小闭环的构成（一条都不能少，少一条就证不了机制成立）：**
登录（走白名单特权路径）→ 注册（白名单事务）→ 1 个 API route（会话面 ALS）→
1 个 RSC page（RSC 执行上下文）→ 1 个例程（无会话面 + scheduler 上下文）→ 跨租户零行（DB 层证据）。

**未覆盖入口必须显式落盘**（F007）：清单 = 全部入口 − 最小闭环已覆盖，不许「剩下的以后再说」。

### D-7 · 执行车道与编排

- **车道：本地异构**（已消费的签名 checkpoint，非本会话可改）。Generator=`local-cli--kimi--generator`，
  Evaluator=`local-cli--codex--evaluator`，`model_family` 分别为 kimi / codex（互斥，独立性铁则第 5 条满足）。
- **building 串行**，不并行：F001→F002→F003→F004→F005/F006→F007 是真实依赖链（后者的测试要 import 前者的导出），
  文件集重叠，不满足 `orchestration-patterns.md` §3 的并行前提。
- **verifying 不 fan-out**：外部 CLI evaluator 是单进程派发，fan-out 的前提（同会话可并发起多个隔离
  subagent）不成立。按 `dispatch-mode.md` 单派一轮。
- **异构风险如实登记：** 上一次异构首跑零验收结论（codex 认证两难 ×2 / kimi 墙钟 ×1 / 本机 DNS 瞬断 ×1）。
  kimi 的 `timeout_s=3600`（`.agents-registry.json` 实物）。
- **派活失败的正规处置 = 硬停，不是回落车道**（2026-08-06 更正）：`dispatch-mode.md` §3.4 写死
  「重派上限 1 次，仍不过 → `generator_cannot_deliver` 硬停 + 通知，绝不静默无限重跑」。
  该文件**没有**任何「回落隔离 subagent」条款。
  > 本段初稿曾写「按 dispatch-mode.md 回落隔离 subagent」——**属失实引用**，已更正。当时是照
  > `project-status.md` 对 M5 的记述（「回落隔离 subagent」）反推该文件有此授权，而未核该文件本身。
  > 这正是 M5 复验点名的 I-2/I-4 同款错误（「与 X 一致」≠ 核证过 X 的性质，铁律 13）。
- **车道在批次中途不可改**：`consume-mode-intent.sh:155-156` 只允许在 `status ∈ {new, done}` 消费模式意图，
  active batch 硬拒。因此若需切回快车道，唯一合法途径是走到批次边界（done 或重新划批），
  不得在 building 期改写 `progress.mode_intent` / `role_assignments`。

### D-8 · 断言强度（继承 `audit-methodology.md` §7，本批逐条落死）

1. 凡「不得漏包裹 / 不得越白名单 / 不得残留」类否定断言，**必须配变异证活**：先构造一个必须让它红的
   改动，实跑看它红，红了再还原。只写断言不证活 = 未交付（M4.6 规律 3、M4.7 三轮 4 例的直接教训）。
2. 变异还原**不得用 `git checkout`**（会抹掉未提交的正身编辑，M5 踩过）。
3. 「0 findings」的 grep 判据必须先证明它能看见目标（`audit-methodology.md` §8）。
4. 交付叙述必须有机械依据（**铁律 13**）：commit 正文 / `generator_handoff` 里每一句「已修 / 已验证 /
   已移除 / 全绿」，落笔前必须有一条命令输出作依据，拿不出就写「未核」。
