## 3. 关键设计决策（增量）

### D-9 · 补验滞后于建造 —— 已知代价，显式登记（用户 2026-08-07 实答）

本批把「F001 补验」与「F002–F007 建造」放进同一批。状态机顺序决定：**`executor:evaluator` 的
F001 落在 verifying 阶段，即在 F002–F007 建完之后才验。** 也就是**在一个尚未独立验证的底座上
先盖了六层**。

**这一点在立项时已向用户明示，用户选择了这个方案。如实登记，不粉饰：**

- **风险：** 若 F001 被判 FAIL，返工面是整批，而不只是 F001。代理形态（D-1）若不成立，
  F002 的 `withTenant` 嵌套语义、F004 的 15 处事务迁移都建立在错误前提上。
- **本批不做的缓解：** 不为此拆批（拆批已试过一次，代价是多一个批次周期）。
- **本批要做的缓解（写进 F002 acceptance 之外的批次纪律）：** Generator 在 building 期若发现
  F001 的机制存在与 spec D-1/D-4 不符的实物，**必须立即停工提 pre-impl 审计**
  （`pre-impl-adjudication.md`），不得「先绕过去再说」。这是把「早发现」从运气变成义务。

### D-10 · F001 补验的判据口径（防两种误判）

F001 的 acceptance 六条原文存档在 `docs/specs/M5.1-F001-unverified.json`（`verified: false`）。
补验时有两个必须先讲清的口径问题：

1. **验的是「批末的树」，不是 `e6ecef1` 那个快照。** F002 会往 `tenant-scope.ts` 加嵌套语义、
   F004 会改 15 处事务调用点、F008 会改两条注释 —— 这些都是**合法的后续扩展**，不构成 F001 的缺陷。
   判据是：**F001 acceptance 描述的性质在批末是否仍然成立**（三层分工、代理三分支、raw 转发、
   开关关时逐位不变），而不是「文件有没有被动过」。
2. **acceptance ② 的「diff 不含 tests/ 与除 `src/lib/db/` 外的 src/」在本批不再适用于原字面。**
   该条是针对 M5.1 那次单 feature 交付的边界约束；本批 F002–F007 本就要改这些地方。
   补验时该条改判为：**「开关关时行为与 M5.1 之前逐位不变」这一实质性质是否仍成立**
   （全量 vitest 绿 + 既有测试文件未被为迁就 RLS 而翻修）。

> 这两条不是放宽标准，是**防止用过期字面把合法演进误判成 FAIL**，同时**防止用「批次变了」当借口
> 把实质性质放过**。两个方向都要防。

### D-11 · acceptance ⑤ 的两条变异证活是硬门，收编证不了它

M5.1 的收编（`accept-generator-handoff.sh`）证的是：沙箱 diff 与 `files_touched` 对账、
L1 在快照重跑、禁改清单未触及。**它不知道那些测试有没有鉴别力。** 所以本批补验必须实施：

- 把代理 (c) 分支的抛错改成「回落运行时 client」→ 对应用例必须红
- 摘掉代理对 raw 方法的转发 → acceptance ④ 的用例必须红

**变异还原不得用 `git checkout`**（会抹掉未提交的正身编辑，M5 踩过）。
只读代码判断不算证活（母 spec D-8.1）。

### D-12 · 两条失实注释的处置归 F008（Evaluator 不写产品代码）

M5.1 的 spec-lock 稽核用 grep 证伪了两条注释（`docs/test-reports/M5.1-F001-spec-lock-review.md`）：

| 位置 | 现文 | 实测 |

| `src/lib/db/runtime.ts:8-9` | 「只有 tenant-scope.ts 与 instrumentation.ts 能 import 本模块」 | 假，两头都错 —— 真实 importer 是 `prisma.ts:23` 与 `tenant-scope.ts:19`；`instrumentation.ts` 并不 import runtime |

### D-13 · 母 spec D-5 引导点表的三处更正（Planner 裁决，2026-08-07）

> **角色切换标注（pre-impl-adjudication.md §4.6）：** 以下为 **Planner** 段。触发源 = F003 开工时
> 按 acceptance ① 重跑普查，实测与母 spec `M5.1-TENANT-INJECTION-spec.md` D-5 的表不符。
> 母 spec 的表自身标注为「起草时刻快照，不是白名单的真相源」，本段据实修正，**母 spec 不追改**
> （它是 M5.1 的历史记录；以本段为准）。

母表 7 条 / 4 文件 → 实测 **8 处 / 6 文件**：

1. **漏列 2 个文件（补入白名单）**：`src/app/api/auth/register/route.ts` 与
   `src/app/api/auth/[...nextauth]/route.ts` 的限速留痕。二者分别发生在**解析入参之前**
   与**会话建立之前**，此刻既无会话也无租户，留痕写的是审计占位租户的行。
2. **`src/instrumentation.ts` 的判定有误（移出白名单）**：母表把启动哨兵列为「引导点，
   应走 privilegedDb」。**该判定错误** —— 哨兵的职责就是「问应用运行时连的是谁」，
   指向恒特权的 `privilegedDb` 会让它恒答「特权」，`enforced` 时永假警报。
   它应显式使用 `getRuntimeDb()`，归 **db/runtime** 白名单。
   > 附带发现（本批修复）：改动前该处传的是 `prisma` 代理。开关开时无 ALS 作用域 → 代理抛
   > `MissingTenantScopeError` → 被 `app-role.ts` 的「连不上库只告警」catch 吞掉。探针实测
   > 得 `{"info":null,"enforced":true,"status":"unknown"}`：**M5 专为「连接串被配回特权」造的
   > BYPASSRLS 哨兵，在 `DB_APP_ROLE_RUNTIME=1` 之后会静默失效。** 安全装置无声死亡比崩溃更坏。
3. **行号漂移（无实质影响，记录以免后人对不上）**：`writeAuthAudit` 实为 `index.ts:51,70`
   （母表写 `:53,:72`）；注册的注入缝实为 `register.ts:99` 的 `deps.db ?? defaultPrisma`
   （母表写 `:107` 的 `$transaction` 行）。

**白名单 as-built（5 文件）**：`lib/auth/index.ts` · `lib/auth/register.ts` ·
`lib/agent/context.ts` · `app/api/auth/register/route.ts` · `app/api/auth/[...nextauth]/route.ts`。
`lib/auth/audit.ts` **不入**：它经 `db: AuthAuditDb` 参数收 client，注入缝在调用方。

## 4. 承接的三条硬约束（来自 M5.1 spec-lock 稽核，不得遗漏）

1. **F002 不得以「F001 已实现 `set_config`」抵扣其 acceptance ①(a)**，仍须交 `set_config` 断言
   + 「第三参 `true` 改 `false` → B3 回归必须红」的变异实跑。若 F002 的交付叙述出现
   「已在 F001 落地，此处复用」而无新增用例 → 当场判 VIOLATION。
2. **F003 须显式决定**要不要把 `tests/` 侧的 `db/privileged` / `db/runtime` importer 纳入普查钉
   射程（其 acceptance ③ 现只写 `src/`）。决定写进代码注释，不得默认略过。
3. `withTenant` 目前**无嵌套守卫**，嵌套会静默开第二事务（B1-4 病灶形态）。当前因产品代码零调用点
   而不可达，但 **F002 落地前是 fail-open** —— F004 迁移事务调用点时若早于 F002 完成，会真实踩中。
   **故 F002 必须先于 F004。**
