## 2. 审计发现

### 2.1 发现 A —— 处置②（入口层带上 timeout）会毁掉 execute 的失败态留痕与票据消费

`executePendingAction`（`src/lib/agent/gate/gate.ts:299-412`）刻意是**三段独立事务**：

| 段 | 内容 | 为什么必须独立提交 |
|---|---|---|
| ① 认领 | 原子条件 UPDATE → `status='executing'` + `ticketUsedAt` | 票据**消费**必须先于副作用落定，否则失败后票可重放 |
| ② 副作用 | `withTenant(…, { timeout: 90_000, maxWait: 5_000 })`：外呼 + `executed` + irrev 留痕 | G5「要么都成功要么都回滚」 |
| ③ 失败收尾 | `status='failed'` + auto 痕 | 设计上就指望它**活过 ②的回滚** |

入口层一包，三段合并成**一个**事务，③ 随 rethrow 一起回滚。

**实测（探针 `scripts/test/m52-f001-gate-tx-probe.ts`，`DB_APP_ROLE_RUNTIME=1` 真连 kol_app）：**

```
[P1] 外层有作用域 + 内层带选项 → NestedTransactionOptionsError
[P2-A 作用域下沉（处置③）] status=failed     ticketUsedAt=已消费          failed留痕=1  irrev残留=0
      ↳ rethrow 前（事务内可见）: status=failed ticketUsedAt=已消费
[P2-B 入口层单事务（处置②）] status=confirmed  ticketUsedAt=null（票可重放）  failed留痕=0  irrev残留=0
```

P2-B 那行 `↳ rethrow 前` 是关键对照：两行**确实写成功了**（事务内读得到），
事后消失只可能是被回滚带走。于是处置②的代价不是「事务持有 90 秒」，而是：

- **`status='failed'` 丢失** —— 直接违反 F001 acceptance ③「闸门语义零回退」，
  且 `gate-smoke.ts:477` 的 G7 断言与 `tests/integration/f004-transaction-atomicity.test.ts:360`
  都钉着这一条；
- **`ticketUsedAt` 回滚 → 一次性执行票变成可重放** —— 这是安全面回退，不只是留痕缺失。

> 补充：处置②如 spec 字面所写（只在外层带 timeout）其实**不成立**——内层那次调用只要还带着
> 选项就照抛 `NestedTransactionOptionsError`（P1 实测）。它必然还要把 gate.ts 的选项摘掉，
> 而摘掉之后，从**无外层作用域**的路径（脚本 / 测试 / agent loop）调 execute 时，
> 那 90 秒就静默变回默认 5 秒——正是 `NestedTransactionOptionsError` 头注点名要防的那种
> 「只在生产超时才现形的坑」。

**M5.1b 已经撞过同一堵墙**并留了记录（`tests/integration/f004-transaction-atomicity.test.ts:279-287`）：
> 「从外层作用域里调它 = 嵌套时再传选项 → 当场抛 NestedTransactionOptionsError……于是这一处必须换一种判据。」

### 2.2 发现 B —— 用户裁决①排除的 29 条探针里，有 9 条是活的 npm script，其中 5 条被本批 acceptance 点名

spec §7 给排除 `scripts/test/` 29 条的理由是「当前无人跑它们（**不在任何 npm script 的默认路径上**）」。
**这句对其中 9 条不成立**（`grep` 逐条核 package.json）：

## 3. 两条决议请求

### 决议 1 · execute 路由的处置：请裁 ③（作用域下沉进 gate.ts），而非 ②

**Generator 建议：处置③**，理由是 §2.1 的实测——②会拆掉两条不变量，而③在实测里
逐条保住（`status=failed` · `ticketUsedAt` 已消费 · irrev 回滚干净）。

具体做法：`/api/actions/[id]/execute/route.ts` **不在入口层包**；改为把作用域下沉到
`executePendingAction` 内部，三段各自 `withTenant`——② 那段保留现有
`{ timeout: 90_000, maxWait: 5_000 }`（它此时是最外层，选项生效）。

**代价，如实登记（请一并裁）：**

1. 该 route 文件本身不含 `withSessionTenant`/`withTenant(`，普查钉判它**未覆盖** →
   F001 已覆盖数 **+4 而非 +5**，F008 的收口目标随之从 **47 → 46**。
   （隔离本身不打折：作用域只是从入口层挪进了领域层，execute 路径的每一次数据访问仍在
   `withTenant` 内。但 acceptance 里那个数字要改。）
2. 另一条路：让普查把「领域层自带作用域」的入口也算覆盖。**不建议**——那等于让量尺跟着
   被量物走，M5.1c 刚为判据可信度付过一批的账。

其余 4 条（`actions/route.ts` · `[id]/route.ts` · `confirm` · `reject`）无此问题，
照样板 `withSessionTenant` 正常包裹（它们没有「靠后续独立事务收尾」的结构）。

### 决议 2 · 那 9 条活 npm script 怎么办

裁决①的前提（「无人跑」）对它们不成立，请在三条里选：

| 选项 | 内容 | 代价 |
|---|---|---|
| **2-A**（建议） | 把这 **9 条活探针**接进本批范围，其余 20 条仍排除 | 范围 44 → 53 条；F002–F004 的「仍绿」才有可能兑现 |
| 2-B | 只接被 acceptance 点名的 **5 条** | 范围 44 → 49；`agent:smoke` / `orch:smoke` / `frontdesk:e2e` / `db:smoke` 留作开关开着时的已知红 |
| 2-C | 维持 44 条，改 acceptance | F001③ / F002③ / F003③ / F004④ 的「开关开着仍绿」降级为「开关关着仍绿」，
本批**不再有**闸门/触达/交付/洞察语义在开关下的行为级证据 |

> 提醒：选 2-C 等于本批只证明「入口包上了」，不证明「包上之后闸门与各域语义没坏」。
> 而 spec §1 的立论正是「把入口包上和把开关打开是同一件事的两半」。
