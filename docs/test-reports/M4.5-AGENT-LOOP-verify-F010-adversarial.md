## 1. 先问「这两条是否落在 F010 的 acceptance 面内」

`features.json` F010 acceptance 原文（逐字）：

`docs/specs/M4.5-AGENT-LOOP-spec.md` 相关口径：

- §58 F010 行：与 acceptance 同义，无清理段/teardown 要求
- §73「零新增对外副作用」：「验收报告须核证**零真实外呼 / 暴露 / 资金动作**」

**结论（对 G5 不利的一半）：** 「零外呼零真实副作用断言」在本项目词汇里指**真实外呼 / 真实公开暴露 / 真实资金动作**，不是 dev 租户的夹具行。acceptance 全文**没有一条**要求 e2e 脚本的 finally 清理段在失败路径上保持健壮，也没有一条要求 dev 租户留痕归零。**两条发现都不在 F010 acceptance 的字面面内。**

> 写 e2e/验收脚本的 finally 清理段时，逐类副作用核对其落库行的实际键位。

### 2.3 尝试证伪的四条路径，逐条结果

| 证伪路径 | 结果 |
|---|---|
| **是否环境误报？** 对照 `testing-env-patterns.md` §3（prisma generate）/ §4（Node 版本）/ §5（E2E flakiness）/ §6（RLS） | **不是。** 复现 100% 确定（触发类变异 2/2 必现，非触发类 1/1 必不现），与 Node 版本、并发、RLS、生成器新鲜度均无关；机理由只读探针独立坐实 |

### 2.4 触发面宽窄（严重性校准的关键量化）

脚本共 **24** 条 assert（`grep` 实测）。相对 `:262` 的 push：

- **15 条**（`:160`–`:257`）在 push 之前失败 → `createdPA` 为空 → 清理段完整跑通（C 组实证残留全 0）
- **9 条**（`:263`+）在 push 之后 —— 但只有当 `pendingIds` 含 `undefined` 时才崩；若为真 id，清理正常

→ **崩溃触发面 = 1 类失败（output 缺 `pendingActionId`），不是「任何 e2e 失败」。** G5 原文「fixing 轮里 e2e 失败是常态，而这正是清理最需要生效的时刻」在**这一类**失败上成立，对其余 15 条不成立 —— 属**表述外扩**，需校准。

**另附一条 G5 未提、但同源的潜伏面（我方补充）：** `pendingIds` 由 `run2.toolOutputs` **全量** map 而来。若将来有人给 run2 的 mock 脚本加一步非 outbound 工具调用，其 output 天然无 `pendingActionId` → `undefined` 入数组 → **在没有任何产品回归的情况下**也会撞同一崩溃。这条使 ① 的修复价值高于其当前触发概率。

### 2.5 裁定 ①

> **UPHELD（维持）**，附严重性校准。

- 机理、复现、残留数字、诊断掩盖 —— **四项全部独立复现，无一项被证伪**
- 排除环境误报、排除人造变异专属、排除并发/版本因素
- 校准项（应写进 feedback，不改变裁定）：
  1. 触发面为 **1/24 失败类**，非「任何失败」
  2. 边际残留为 **4 logs + 1 handoff + 1 project**（非 6/2/1/1；其中 2 shares + 2 logs 属发现 ② 同族，G5 建议修法也删不掉）
  3. 影响面 **100% 限于交付脚本**，零产品代码，零用户可见面；修复量 ≈ 2 行（`filter(Boolean)` + 清理段逐步 try/catch）
  4. 减责事实：patterns §9 虽先于本批入库，但记忆索引把该文件路由给 **Evaluator** 角色，未路由给 Generator（§1 末）

### 3.1 事实复现（2/2 必现）

| 快照 | logs | 增量 |
|---|---|---|

| 原样跑第 1 次（exit 0，24 断言全绿） | 108 | **+2** |
| 原样跑第 2 次（exit 0） | 110 | **+2** |

新增行的键位（快照原样，非推断）：

```json
{"kind":"auto","ref":null,"projectId":null,"summary":"create_share_link:SHARE_CREATED 已生成 quarterly 范围分享引用 …（mock 未外呼…）"}
```

### 3.2 但「判定影响」被引申了 —— 逐条核对 G5 引用的口径

G5 原文：*「按 `evaluator.md` §14(c)『soft-watch 缺明文兜底即验收不闭环』，需要 Generator 二选一…」*

**核对 1：这条口径是否真实存在？** —— **存在，且引述准确。**
`evaluator.md:225,227`（同 `framework/harness/evaluator.md`）逐字：

> (c) **所有 Soft-watch 项有明文兜底机制** | 每条 soft-watch 必须在 progress.json / spec / signoff 中明文写兜底 …
> 即便代码层全 PASS，**soft-watch 没兜底 = 验收不闭环**。

→ **不是杜撰，不是引申措辞。** 这一点必须如实认账。

**核对 2：这条口径的适用对象是什么？** —— **是「批次能否切 done」，不是「单 feature 判 PASS/PARTIAL」。**

- §14 标题：**「首轮 verifying PASS（fix_rounds=0）的**硬条件**」**，全节讨论的是 `verifying → done` 一步到位的准入
- 决策路径第 5 步：「缺任一兜底 → 标 FAIL，回 Generator 补」
- 规定的**补救物是一份文档**：「把兜底机制写进 progress.json 或 spec」

**核对 3：本项目对**这一族残留**有没有已生效的先例？** —— **有，而且是同族同因。**

| 证据 | 原文 |
|---|---|
| `docs/test-reports/M4-INSIGHT-signoff-2026-07-25.md:164` | 「唯一持续副作用 = `insight:e2e` 每跑一次 dev 租户 `OperationLog` 净增 1 行（append-only 语义，本轮终态 104 行，见 soft-watch S5）」 |
| 同文件 `:184` S5 | 「…每跑一次 `insight:e2e` 再 +1 行…**e2e 副作用不建议改成删日志（违 append-only 语义）**」 |
| `.auto-memory/project-status.md:21` | 「O2（insight:e2e 每跑净增 1 行 marker OperationLog，**append-only 语义一致不建议删，仅知晓**）」 |
| `patterns/testing-env-patterns.md` §9 注 | 「append-only 语义的留痕表也可**选择保留不删** —— 但必须知晓其后果…删或留是一个**显式决定**」 |

三处一致：**这一族残留的既定处置是「保留 + 明文登记」，并且明确写着「不建议删」。** M4 该批并未因此把 F012 压低，也未为此起一轮 fixing —— 登记它的文档（signoff）本来就是 **Evaluator 自己写的**（`evaluator.md` §8）。

**核对 4：G5 是否已经完成了登记？** —— **接近但差一步。** G5 §7 S-G5-2 已把该项列表登记，但处置写成「精确清理 **or** 明文登记，二选一，Generator 定」—— 这是**待决选项**，还不是 §14(c) 要求的**兜底承诺**。缺口是真实的，但缺的是**一句处置定论**，而这句话按项目先例应由 **Evaluator 在 signoff 写定**，不需要一轮 fixing 来产生。

### 3.3 裁定 ②

> **DOWNGRADED（成立，但严重性/判定影响降级）**

- **事实层：UPHELD** —— 2/2 必现，键位与 G5 描述逐字一致，未被证伪
- **判定层：DOWNGRADED** —— 从「F010 判 PARTIAL 的依据之一」降为「**必须在 signoff §Soft-watch 写定处置的 soft-watch**，不降 F010 判定」。理由三条：
  1. §14(c) 的适用对象是**批次切 done 的准入**，其补救物是**一句明文兜底**，不是 feature 级降档
  2. 本项目对同族残留已有**生效先例**（M4 S5 / O2 / patterns §9 注），且先例结论是「**不建议删**」——若照 G5 的「二选一」让 Generator 去删，反而与既定口径冲突
  3. 登记权在 Evaluator 手上（signoff 由 Evaluator 撰写），一句话即可闭环
- **降到什么程度：** low / soft-watch，**单独不足以把 F010 压到 PASS 以下**。建议照抄 M4 S5 口径写定：*「`agentloop:e2e` 每跑净增 2 行 SHARE_CREATED 标记 OperationLog（`ref`/`projectId` 皆 null）；append-only 语义一致，不删；知晓其后果 = 会进 dev 租户活动流，本机含 feed 的视觉基线重生前须一并计入」*

## 4. 对 F010 的最终建议判定

> **PARTIAL —— 维持 G5 结论，但支撑点从「两条」收窄为「一条」，且严重性重新定级为 low / 交付物级。**

**为什么不能翻成 PASS：**

- 发现 ① 的每一个可检验元素（Prisma 拒绝语义、push/assert 顺序、finally 首句崩溃、ASSERT FAIL 被掩盖、残留行数）**在隔离沙箱里 100% 复现**，无一被证伪；不属任何一类已知环境误报
- 它违反的是**先于本批 8 小时入库**的项目 pattern（`testing-env-patterns.md` §9「清理段逐类核对键位」「删或留必须是显式决定」），不是我或 G5 新造的期望
