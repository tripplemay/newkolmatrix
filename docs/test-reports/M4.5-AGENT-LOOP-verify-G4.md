## 5. 观察项与验证缺口

### 5.1 [F004 · 观察 O1 · 低] plan-ack 的兜底 catch 与全站闸门路由不同款

`api/agent/plan-ack/route.ts:35-39` 对**任何**非预期错误返回 `error.message` 原文 + **400**，且不 `console.error`。实测 404 响应体：`{"error":"[plan-ack] 计划不存在: g4-no-such-plan"}`（内部前缀原样外泄）。同批 `/api/actions/*` 的 `gateErrorResponse`（`lib/agent/gate/http.ts:41-53`）口径是「泛化文案 + 500 + 服务端 log」。DB 故障 / dev tenant 缺失这类服务端问题会被报成 400（客户端的错）并静默——与 spec P2 引用的「logEvent silent-fail 教训」同族。
**不影响 acceptance 判定**（本条不在 acceptance 内，且无闸门/红线含义）。建议后续统一到 `gateErrorResponse` 口径。

### 5.2 [F004 · 观察 O2 · 低] 幂等是 read-then-write，无唯一约束兜底

`acknowledgePlan` 先 `findFirst` 再 `create`，无 DB 级唯一约束。12 路并发认可实测 **1 行**（3 次复跑稳定 1 行），未观察到重复。理论竞态窗口存在，最坏后果是**审计留痕多一行**——该端点零执行权（O7 红线已单独钉死），不构成闸门风险。如后续要求强序列化，需加部分唯一索引或 upsert。

### 5.3 [F008 · 验证缺口 · **L2 未授权，待授权**] 真网关下的分片下发

离线已证实的部分（本轮新增，非 Generator 原登记范围）：
- SDK 装配层：`tool-input-delta` → `state:'input-streaming'` 的 partial input（§3.2 21 帧实测）；`readUIMessageStream` 与 `useChat` 共用同一 `processUIMessageStream`（`ai/dist/index.js:6506` 被 :7192/:10296/:16827 三处复用）
- Provider 层：项目走 `createOpenAI(...).chat()` = `/chat/completions`（`lib/ai/gateway.ts:142`），该路径的 `StreamingToolCallTracker`（`@ai-sdk/provider-utils/dist/index.js:3540+`）会把 `delta.tool_calls[].function.arguments` 分片转成 `tool-input-start/delta/end`；`toUIMessageStream` 对这三类片**无条件透传**（`ai/dist/index.js:9465`，无 `toolCallStreaming` 开关）
