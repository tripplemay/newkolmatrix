本组补了 `scripts/test/m45-g5-gate-http-chain.ts`：让 `confirmAndExecuteSequentially` 的传输层**直驱真 route handler**（含 `params` Promise、`gateErrorResponse` 分码、限流 guard）：


### 4.5 缺陷（判 PARTIAL 的依据）

#### ① `agentloop:e2e` 的清理段在**失败路径**上整体崩溃 → dev 库被污染（主要）

`scripts/test/agentloop-e2e.ts:259-262`：

```ts
const pendingIds = run2.toolOutputs.map((o) => (o.output as {…}).pendingActionId!);
createdPA.push(...pendingIds);            // ← 先 push
assert(pendingIds.length === 2 && pendingIds.every(Boolean), '2 件都落 pending');
```

当 outbound 不再返回 pending 信封（= 闸门红线回归，正是这条 e2e 最该抓的事），`pendingIds = [undefined, undefined]` 先被 push 进 `createdPA`，随后 `finally` 的第一句 `deleteMany({ where: { gateLogId: { in: createdPA } } })` 被 Prisma 拒绝（`Can not use undefined value within array`）→ **整个清理段中断**，且原始的 `ASSERT FAIL` 信息被这个二次抛错盖掉。

实测后果（我在变异测试里连撞两次，逐行核过）：dev 租户净增 **12 条 OperationLog + 4 条 ShareLink + 2 条 Handoff + 2 个 Project**，全部由我用 `scripts/test/m45-g5-cleanup-diff.ts` 按 id 差集手工回删。

危害不是假设：`fixing` 轮里 e2e 失败是常态，而这正是清理最需要生效的时刻；被污染的 dev 库会直接把本机含 feed / 雷达的视觉基线打红（`patterns/testing-env-patterns.md` §9 记的 M3-A「today feed 基线污染误判」就是同一族），下一个隔离 evaluator 会把它当产品回归。

**复现步骤**（约 2 分钟）：

## 8.5 推送前 L1 复核：探针自身的 tsc 与 CI 环境适配（2026-07-25，编排方反馈后）

### 8.5.1 改了什么（只动本组探针 `tests/integration/m45-g5-f006-f007.probe.test.ts`）

| # | 问题 | 修法 |

### 8.5.3 CI 环境实证（不靠推断）
