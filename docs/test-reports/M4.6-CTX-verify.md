### 4.1 跨租户取名实测（soft-watch S1 的事实化）

`findProjectByRef` 无 `tenantId` 条件，而 `copilot.projectId` 是**客户端可控**的（`route.ts:63` 直接取 `body.context.projectId`，不校验归属）。实测（一次性脚本，已删）：

```
ctx.tenantId  = cmrrlq75d…  (dev)
project 所属  = cms1ci9z9…  (另一个租户)
system 段是否含另一租户的项目名 => true
system 段节选: 【当前上下文】用户正在项目 cms1ci9zb…（SECRET-别的租户的项目名-55953） 的页面上与你对话。
零外呼: []   夹具残留: 0
```

当前单租户（dev）下**无实际影响**，且工具执行仍按 `ctx.tenantId` 作用域（跨租户 id 填进工具会 `PROJECT_NOT_FOUND`），故不判缺陷。但 `findProjectByRef` 是**新导出的可复用口径**，注释明写"新代码一律走这里"——若被任何持有 ctx 的工具复用，就会静默丢掉租户隔离。M5（真实认证 + RLS）之前必须收口。

### 4.2 交付测试产物的清态缺口（批内引入，实测可复现）

`OperationLog` 与 `Handoff` 对 `Tenant` 是**软引用无 FK**（`schema.prisma:768/792`，仅 `@@index([tenantId])`），删租户**不级联**。而 `project-context-injection.test.ts` 的 `afterAll` 只删 `project` + `tenant`，其两条 `runScriptedLoop` 用例会产生：接力那条 → 1 行 `Handoff` + 1 行遥测 `OperationLog`；真 loop 那条 → 1 行遥测。

实测（本地 dev 库，跑一次交付用例前后计数）：

```
BEFORE  OperationLog: 172  Handoff: 25
（跑 npx vitest run tests/integration/project-context-injection.test.ts → 9 passed）
AFTER   OperationLog: 174  Handoff: 26        ← 每跑 +2 / +1，且最近两行经 tenant 存在性核对为 *** 孤儿 ***
```

盘点全库：孤儿行（tenantId 在 `Tenant` 表中已不存在）**OperationLog 66 行 / Handoff 30 行**，其中 30/15 行由我本次会话产生（已按 `createdAt` 窗口精确清除），**余 36 行 OperationLog + 15 行 Handoff 为本会话之前既有**——即作者自己跑该文件约 15 次的沉积，留作 fixing 轮的证据不动。

不污染 dev 租户（孤儿行不属 dev，dev 视觉基线不受影响），故不是 blocker；但它与 `patterns/testing-env-patterns.md §9`（清态必须按业务标记逐类核对落库键位）同族，且该文件 `afterAll` **只断言 tenant 残留 0**，给出"已清干净"的假信心。守门 `tests/unit/e2e-cleanup-hygiene.test.ts` 只覆盖 `scripts/test/agentloop-e2e.ts`，覆盖不到 vitest 集成测，故无机械拦截。
