## 2. 论断① · F007「产品侧无超时闸」→ **UPHELD（核心成立，两处事实更正）**

> **原文（G3 §4.1 / S-M47-G3-8）**：「产品侧无超时闸——子 loop 挂死会一路挂到平台 `maxDuration=120s` 被整体截断，前台没有机会说『我问了但没拿到结果』；测试里的『超时支』是同一条抛错路径改名。」

### 2.1 成立的部分

| 子主张 | 裁定 | 我的独立证据 |
|---|---|---|
| 子 loop / 主 loop / chat 路径**无任何墙钟自限** | ✅ 成立 | **P9**：`specialist-loop.ts` / `consult-specialist.ts` / `loop.ts` 三个文件里 `abortSignal\|AbortSignal\|Promise.race` 命中数 **0**；`gateway.ts` 唯一命中是 `:171 signal: AbortSignal.timeout(AIGC_TIMEOUT_MS)`，属 `embedText` 直连，chat 走的 `resilientFetch`（`gateway.ts:102-117`）**不传 signal**，`generateText` / `streamText` 均未配 `abortSignal` |
| 挂死时前台拿不到发言机会 | ✅ 成立（在任何可用窗口内） | **P10**：注入 `doGenerate` 永不 settle 的模型，走**完整** `runAgentLoop` → 消费 `textStream` 与 5s 定时器竞速 → `winner="timer"`、`text=""`。前台第二步本该出「（前台收尾）」，一个字都没出来 |
| 测试的「超时支」= 抛错支改名 | ✅ 成立 | `consult-failure.test.ts:74` 与 `:97` 都是 `vi.spyOn(specialistLoop,'runSpecialistLoop').mockRejectedValue(...)`，**同一条 catch**；两条用例的差别只是 Error message 写「网关连不上」/「专家超时」，且第二条的用例名本身写的是「失败必须落 OperationLog」——它压根不是一条超时用例 |

### 2.2 被证伪的两处因果叙述

**更正 A · `maxDuration=120s` 不会截断任何东西（自托管形态下是死配置）**

- `route.ts:32-34` 的注释**自陈**：「self-host standalone **无平台上限**，这是纯配置数字（Vercel 托管才受套餐封顶）」。本项目部署形态即 standalone（`docs/dev/deploy.md:4`「app（standalone 运行镜像）」）。
- **P13**：`next.config` 内 `maxDuration|timeout` 命中数 **0**——没有任何地方把这个 120 落成真实的墙钟。
- 结论：论断①里「被整体截断」这一步**在本项目的部署形态下不发生**。

**更正 B · 挂死不是"永远挂"，而是"~301 秒后才由 undici 兜底"**

```
node=v25.7.0
REJECTED afterMs=301018 name=TypeError msg=fetch failed causeCode=UND_ERR_HEADERS_TIMEOUT
```

- 这是本轮对「连上但永不回响应头」的上游做的墙钟实测。Node 全局 fetch（undici）默认 `headersTimeout ≈ 300s`，最终会抛。
- 而**抛之后的整条链路是通的**：**P12** 用一个在**模型层**抛 `TimeoutError('The operation was aborted due to timeout')` 的 mock（不 spy `runSpecialistLoop`，走完整 `specialist-loop → catch` 链）实测得到 `{ok:false, failureReason:"The operation was aborted due to timeout", answer:""}` + `consult_specialist:FAILED` 留痕 **1 行**。
- 因此 D-4 承诺的那句话**不是"不可达"，是"迟到 ~301 秒才可达"**——超出 `maxDuration` 名义预算的 2.5 倍，超出任何用户耐心与前置反代超时，工程上等同不可用，但**性质不同**：缺的只是一个 deadline，而不是整条降级链路。

### 2.3 定性：缺的是产品能力，但**不是 F007 的能力，也不是子 loop 专属**

- **P11**：把主 loop 自己的 `doStream` 换成永不 settle → 同样 3s 定时器胜出。**主 loop 与子 loop 暴露完全相同**。
- 该缺口自 AGENT-FOUNDATION（`chatModel()` 从来没配过超时）就存在，`M4.5-AGENT-LOOP-verify-G2.md:89` 当时甚至把它记为一条**正面**事实（「无隐藏的分步墙钟上限抵消该预算」）。M4.7 F007 没有引入它。
- F007 自身交付的四项（结构化失败 / 不抛穿 / 留痕 / 条款锚点）对**运行时能够浮出的每一种失败**都是完整且正确的（P12 用真链路复证）。它唯一交付不了的，是"运行时永远不浮出"这一种——而那取决于有没有人设 deadline，D-4 的裁决表通篇是**行为裁决**（"如实说 + 留痕"），没有一句是机制裁决。

**→ 修复归属建议（不改变判定）：** 正确修复点是 `gateway.ts` 的 chat 路径（或 `runSpecialistLoop` / `runAgentLoop` 传 `abortSignal`）一处注入 deadline，加一条**真**超时用例（P12 那种形态：让模型层抛，而不是 spy 掉被测函数）。这是一条独立的可靠性欠账，规模远小于 G3 措辞给人的印象——但**它不能被用来软化 F007 的判定**，理由见 §5.2。

## 3. 论断② · F006「撞任一上限诚实告知只覆盖 2/3」→ **UPHELD（措辞需收紧）**

> **原文（G3 §3.1 #3 / S-M47-G3-3）**：「『撞任一上限诚实告知』只覆盖 2/3——前台自己撞步数顶时用户端零告知。」

### 3.1 acceptance 口径核实（先确认这条要求不是被读宽了）

- `features.json` F006 acceptance 原文：「**撞任一上限时必须诚实告知「未答完 + 还差什么」**」。
- 规格 `M4.7-FRONTDESK-spec.md` D-3 表最后一行：「撞顶行为 | **必须诚实告知**「未答完 + 还差什么」 | 变异测试钉死，不许假装答完」；同表列出的上限含「**总步数硬顶 前台 5 + 子 loop 2×3 = 11**」。
- **无收窄解释空间**：「任一」「总步数硬顶」都在原文里。这条要求确实覆盖前台自身步数顶。

### 3.2 实测（P5，真 `runAgentLoop` + 真 `consult_specialist` 子 loop + 真库）

```
steps                = 5   maxSteps = 5
finishReason         = "tool-calls"
text                 = ""              ← 一个字的答案都没有
toolNames            = [consult_specialist, consult_specialist, propose_plan, propose_plan, propose_plan]
telemetry            = { steps:5, maxSteps:5, budgetHit:true, consultCount:2, … }   ← 只在服务端
streamDataParts      = ["data-persona_switch"]   ← 流内唯一的 data part 种类
```

- **撞顶事实只存在于服务端**：`loop.ts` 的 `budgetHit` 只进 `onEnd` → `OperationLog`；`route.ts` 往流里写的 data part **只有** `data-persona_switch` 一种；响应头只有 `X-Agent-Id` / `X-Agent-Tools`。
- **`CopilotPanel.tsx:227-249` 只用 `status` 做 busy 态**，没有任何错误/截断呈现。流正常结束 → `status='ready'` → 界面就停在那里，用户无从分辨"被预算砍了"还是"答完了但没话说"。
- **这条无法靠 prompt 条款修复**：截停发生在第 N 步之后，模型不会被再唤起，任何写进 `FRONT_DESK_HONESTY_CLAUSE` 的话都没有说出口的机会。**它必须是产品机制**（如 loop 在 `stopWhen` 命中时往流里写一条 data part / 追加一句服务端生成的说明）。

### 3.3 尝试证伪的三条路径，全部失败

| 尝试 | 结果 |
|---|---|
| **M4.5 既有的长链诚实条款是否已覆盖该场景？**（编排者点名） | ❌ 没覆盖。**P8**：`long-chain-honesty.test.ts` 全文 `未答完\|还差什么\|撞顶\|budgetHit` 命中 **0**；它管的是"只拿到 pending 却宣称已发出/已完成"，作用对象是**最终文本**，而撞顶场景下最终文本根本不存在。 |
| **该场景是否本就不可达（低到不必修）？** | ❌ 可达，且路径很现实。P5 里最后三步是 `propose_plan` **连续三次工具错误**——模型把入参写错→重试→再重试，5 步预算就此烧光，用户拿到空回复。这是生产里相当常见的模型行为，不是刻意构造的极端。 |
| **UI 是否有别的兜底把撞顶说出来？** | ❌ 没有。`ConsultationNote.tsx:75-79` **确实**有「未答完」徽标——但它读的是 `output.budgetHit`，即**子 loop** 撞顶（上限②）。前台自身撞顶没有任何等价载荷。这反而让不对称更清楚：上限①有工具错误回喂模型、上限②有条款 + UI 徽标双保险、上限③**两样都没有**。 |

### 3.4 需要收紧的措辞（唯一一处对论断的修正）

「用户端**零告知**」措辞过宽。实测 `visibleToolResultCount = 2`：两张咨询痕迹卡（含「证据不足」等徽标）照常渲染，另有三行「工具 propose_plan 出错」。

**准确表述应为：** 用户端有**痕迹**、无**答案**、无**「未答完 + 还差什么」的说明**，且无任何信号区分"被预算砍断"与"正常结束"。这不影响 acceptance 判定——acceptance 要的正是那句说明。

### 3.5 附带定位（影响修复归属，不影响判定）

**P6**：M4.5 的 `reach` 常规人格撞顶实测同样 `steps=5 / text="" / finishReason="tool-calls"`，且 `long-chain-honesty.test.ts:196-218` **就是这么断言的**——零文本截停是 M4.5 明确记录在案的既有形态。M4.7 没有引入它；M4.7 F006 是**第一次把"撞顶要诚实告知"写进 acceptance** 的批次，因而也是第一次暴露它。

## 4. 论断③ · F009「🔑 断言是同义反复」→ **UPHELD**

### 4.2 e2e 内是否有别的断言守住该性质？——**没有**

`frontdesk-e2e.ts` 全部 13 条断言逐条过：零外呼 / 🔑 受理是前台 / 咨询 2 次 / pending 1 条 / 留痕归属 insight / 副作用零发生 / Handoff +2 / 无失败留痕 / 副作用确认后发生 / 分享留痕 / 遥测落行 / consultCount=2 / 遥测无正文。

最接近的是「咨询了 2 位专家」——若 persona 不是前台，`consult_specialist` 不在 ToolSet 里，这条会翻红。**但它与 🔑 那条同源**：都由测试自己传入的 `agentId` 决定，不是产品在某个决策点做出的选择。**F009 acceptance 明列的「项目环节页发起 → 前台受理（非环节人格）」这一链，在这条 e2e 里确实没有被证明。**

### 4.3 但该产品红线本身是被守住的，且**不是**同义反复

`tests/integration/project-context-route.test.ts:249`（`git blame` → `b0ac691 feat(M4.7-FRONTDESK-F003)`）：

```ts
it('🔑 环节页发起的会话，受理人格仍是前台（本批根因的正面断言）', async () => {
  const r = await postAgent({ …, context: { route:`/admin/campaigns/${projectId}`,

```

它 `import { POST } from '../../src/app/api/agent/route'` —— 走**真 route**、真 `resolveContext`。**输入 `'match'` ≠ 期望 `'orchestrator'`**，是真正有分辨力的断言；根因回归（route 层恢复采信客户端 agentId / 按 stage 推导）会让它翻红。它在 CI 内：`test:unit = vitest run`（跑全仓含 `tests/integration/`），CI 的 test job 跑 `npm run test:unit:coverage`。

### 4.4 残余灵敏度（对 e2e 那条断言的最后一次辩护，我给它记上）

**P4**：e2e 传的 copilot 带 `stage:'match'`。若哪天**装配层**（而非 route 层）开始采信 `stage` 定人格，`run.loop.persona.id` 会变成 `match` → 该断言会翻红。所以它不是**零**信息，是**低**信息：它挡的是一条假想的装配层回归，而不是 acceptance 写的那条「环节页发起」。

### 4.5 附带确认：注释与代码相反

`frontdesk-e2e.ts:75` 写「**刻意传环节人格**：服务层同样不该让它决定受理者」，`:76` 写 `agentId: FRONT_DESK_AGENT_ID`（= `'orchestrator'`，前台）。G4 说它「是与代码相反的陈述」——**属实**，且这是三条论断里唯一一条**下一个读它的人会被直接误导**的缺陷（会以为这条链已经证明过了）。

## 5. 对 F006 / F007 / F009 判定的影响

### 5.1 F006 —— **PARTIAL 维持**

论断②成立且 acceptance 无收窄空间。缺的不是断言而是**产品机制**（撞顶事实必须以某种方式抵达用户端），且 prompt 条款结构上做不到。G3 给的严重度「中」我认为**偏低**：P5 显示触发路径是"模型连续写错工具入参"这一常见形态，后果是用户拿到完全空白的回复且无任何解释。建议在 fix 轮按**中—高**处理。
> 措辞订正：报告里「用户端零告知」应改为「用户端有痕迹、无答案、无『未答完 + 还差什么』说明」。这是表述订正，不改变判定。
> F006 的 PARTIAL 另有 S-M47-G3-4/5/6 三条支撑，本轮未复核（自证类，不在委派范围）。

### 5.2 F007 —— **PARTIAL 维持**

acceptance 第 5 项写的是「**集成测覆盖抛错与超时两支**」。这是一条**测试**要求，而两条用例是同一条 `mockRejectedValue` 路径（§2.1）——该 FAIL **完全不依赖**产品侧有没有超时闸这个争点，无论我对论断①的因果更正如何，它都站得住。
论断①的两处事实更正**不构成软化理由**，但会改变 fix 轮的做法：

## A.2 闭合度判断（编排方问的正题）

### ① 超时闸 —— **基本闭合，1 条残留**

已闭合，且是**真闭合**而非纸面闭合：

**残留 R-3（中）· 超时预算与咨询预算算不拢：**
`MAX_CONSULTS_PER_TURN(2) × SPECIALIST_TIMEOUT_MS(60s) = 120s > LOOP_TIMEOUT_MS(110s)`。
即：**在允许的咨询次数内，两次连续挂死会先撞穿主 loop 闸**——第二次咨询超时前主 loop 已被 abort，前台仍旧一个字说不出来。单次挂死闭合，最坏情形未闭合。三个数字各自都有出处，但没人把它们放在一起算过一次（与 D-3「数字是猜的」同族）。
