## 4. 缺陷清单

### D1 · [F001] acceptance 明列的负向断言「子 loop 内调非目标人格工具被拒」无鉴别力（PARTIAL）

**性质**：交付物（测试）缺陷。**产品行为在 HEAD 上正确**——隔离确实生效。

**事实**：`tests/integration/specialist-loop.test.ts:104-131` 用「洞察硬调 `payout` → 不落 `PendingAction`」承担这条负向断言。但 `payout.inputSchema` 只接受 `dealId`（`src/lib/agent/tools/payout.ts:29-35`），用例传的是 `{ projectId }` → **在 `executeTool` 的 zod 校验就失败**，永远走不到闸门。于是「`PendingAction`=0」**在隔离成立与被击穿两种世界里都为真**。

**实测复现**（worktree `/tmp/m47-g1`，SHA 958c5e4）：

1. 施加 MUT-5：`specialist-loop.ts` 里 `toAiSdkTools(toolNames, …)` → `toAiSdkTools(allPersonaToolNames(), …)`，并删掉 `isToolActive: (name) => target.tools.includes(name)`（= 时刻隔离两道防线全摘）
2. `npx vitest run tests/integration/specialist-loop.test.ts` → **10 passed（全绿）**
3. 同一变异下跑诊断探针（洞察子 loop 依次调 `payout` 与 `create_project`），实测输出：

```
TOOLNAMES ["payout","create_project"]
PA []                                            ← 既有断言看的这一项：仍然是 0（假绿）
PROJECTS [{"name":"probe proj 90993"},{"name":"越权造的项目-90993"}]
                                                 ↑ 越权工具**真的执行了**并落了一行
```

4. 换成本组探针 P1（判据改为「会成功执行的工具 + 行级证据」），同一变异 → **RED**：`越权工具一旦真被执行，这里就会多一行: expected 1 to be +0`

**为什么算缺陷而非吹毛求疵**：本批 spec §6 测试策略第 2 条自订「每条新断言必须附带『什么改动会让它红』，且变异要包含**作者没想到的绕过路径**」；F001 acceptance 又把这条负向断言写成硬要求。Generator 已诚实记录了 MUT-1(摘 isToolActive) 恒绿并据此改了用例名，但**未做「双防线同时放宽」这一步**，留下的断言恰好属于 `.auto-memory` 里反复记账的「取证器看不见目标」类。

**建议修复**（Generator 侧，1 处改动）：把该用例的探测工具从 `payout` 换成在夹具下**必定执行成功**的越权工具（如 `create_project`），判据改为「库里不得多出对应行」；或直接采纳本组 `m47-g1-frontdesk-probe.test.ts` P1。修复后须用 MUT-5 复证翻红。
